WebSocket repair:
- Treat Connect, Send, Close, and Match as a session lifecycle. Inspect sessionName, URL, headers/cookies, action, waitMode, responsePattern/responseBinary, filters and handler placement. Preserve recorded timing and connection ownership unless evidence requires a change. A successful Send only proves transmission, not an application outcome.
- list_recorded_exchanges_open_plan identifies Connect recordings and message counts. get_recorded_exchange_open_plan returns recordedWebSocket with messageIndex, direction, relativeTimeMs, contentType, text and bounded hex/ASCII/base64. Review webSocketCorrelationHints as candidates, not proven dynamic fields. Page with messageOffset/messageLimit and inspect truncation; use search_recorded_exchanges_open_plan to find text, hex or embedded ASCII. These messages belong to the Connect recording, but are NOT its runtime HTTP response. Locate Send/Match targets using stable node IDs and sessionName; sampler names may repeat. The HTTP correlation audit does not cover asynchronous message dependencies.
- Correlate only from a received value that precedes the consuming send in the same session or a proven cross-session flow. Verify the live receive before using its variable. For a request/reply flow, use update_websocket_open_plan to set Send and Wait with an evidence-based matcher, then attach text extractors to that Send's response. For unsolicited messages, update an existing Match under Connect or use add_websocket_match_open_plan with saveMessageVariable; text is stored unchanged and binary as hex. Do not attach a message extractor to Connect's handshake. A later sender must wait for the necessary handler result; a recording timestamp alone is not synchronization.
- Binary validation responseBodyEncoding=hex describes the tool's representation, not the runtime response string. Never apply ordinary text regex/boundary extractors or text assertions to this hex representation. Use raw prev.getResponseData() in a JSR223 postprocessor/assertion, or decode a Match hex variable. For binary sends, payload is hex; variables must expand to valid hex. Decode/re-encode the proven application protocol (including type tags, lengths, framing and byte order) when values change. ASCII is only an inspection aid: dots represent nonprintable bytes. Do not assume MessagePack, protobuf, compression or encryption from hex appearance, replace arbitrary byte substrings, or invent an unsupported decoder. If protocol evidence/codecs are unavailable, report the precise blocker.
- Live edits can use update_websocket_open_plan for existing Connect/Send/Close/Match settings, replace_literal_open_plan for payload variables, and add_jsr223_open_plan for proven byte-aware extraction/re-encoding/assertions. Validate the full session with bounded runs, confirm variables are populated before sends and replies satisfy meaningful application assertions. Preserve disconnect/error reporting and clean up the session; do not declare success solely from 101, send success, or a green run with no application replies.
